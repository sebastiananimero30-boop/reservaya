1. Descripción General del Sistema

ReservaYa es una plataforma web full-stack para la gestión de reservas en restaurantes. Permite a clientes buscar restaurantes, ver disponibilidad en tiempo real y hacer reservas con pago de depósito. Los propietarios gestionan su restaurante desde un panel propio y los administradores controlan toda la plataforma.

4. Backend — Laravel 11

Patrón de Arquitectura

El backend sigue el patrón MVC + Resources. Los controladores reciben la petición, validan los datos, interactúan con los modelos Eloquent y devuelven respuestas usando API Resources para transformar el JSON.

Modelos y Relaciones

User

Roles: client, owner, admin. Métodos helper: isAdmin(), isOwner(). Relaciones: hasMany(Restaurant), hasMany(Reservation).

Restaurant

Usa SoftDeletes. Relaciones: belongsTo(Category), belongsTo(User owner), hasMany(Table), hasMany(Reservation), hasMany(Review), hasMany(Schedule), hasMany(RestaurantPhoto).

Reservation

Estados: pending, confirmed, completed, cancelled, no_show. Campos clave: start_time, duration_minutes (90 min), payment_intent_id, deposit_refunded.

MenuItem

Usa SoftDeletes. Campos: name, category, price, image_url, is_available.

Lógica de Disponibilidad

// ReservationHelper.php
// Una reserva dura 90 minutos. Se considera conflicto si:
// el inicio de la nueva reserva cae dentro del bloque de una existente
// (±90 minutos del start_time)

public static function hasConflict(int $tableId, Carbon $start): bool
{
    $end = $start->copy()->addMinutes(90);

    return Reservation::where('table_id', $tableId)
        ->whereIn('status', ['confirmed', 'pending'])
        ->where(function ($q) use ($start, $end) {
            $q->whereBetween('start_time', [$start->subMinutes(89), $end])
              ->orWhereBetween(DB::raw("start_time + interval '90 minutes'"), [$start, $end]);
        })->exists();
}

Soft Deletes

Los modelos Restaurant y MenuItem usan el trait SoftDeletes. Al eliminar, se registra la fecha en deleted_at sin borrar el registro. Se pueden restaurar o eliminar permanentemente desde el panel de administración.

5. Frontend — React + Vite

Gestión de Estado

Se usa TanStack Query v5 como único gestor de estado del servidor. No hay Redux ni Context para datos remotos. La configuración global está en main.jsx:

const queryClient = new QueryClient({
  defaultOptions: {
    queries: {
      staleTime: 1000 * 30,           // 30 segundos frescos
      refetchInterval: 1000 * 30,     // Auto-refresh cada 30s
      refetchIntervalInBackground: false,
      retry: 1,
    }
  }
})

Adaptadores

El backend devuelve campos en snake_case y el frontend los consume en camelCase con nombres en español. El archivo adapters.js hace esa transformación:

// adapters.js
export function adaptRestaurant(r) {
  return {
    id: r.id,
    nombre: r.name,
    descripcion: r.description,
    direccion: r.address,
    zona: r.zone,
    foto_portada: r.cover_photo,
    mesas: r.tables?.map(adaptTable),
    // ...
  }
}

Interceptor Axios

El cliente HTTP agrega automáticamente el token de autenticación a cada petición:

// axios.js
api.interceptors.request.use(config => {
  const token = localStorage.getItem('token')
  if (token) config.headers.Authorization = `Bearer ${token}`
  return config
})

7. Autenticación y Roles

Flujo de Autenticación

1. POST /api/auth/login  →  { email, password }
2. Laravel valida con Sanctum
3. Devuelve { token, user }
4. Frontend guarda token en localStorage
5. Cada petición incluye: Authorization: Bearer {token}
6. Middleware auth:sanctum verifica el token

Google OAuth

1. Usuario hace clic en "Continuar con Google"
2. Frontend redirige a Google con el Client ID
3. Google devuelve credential (JWT)
4. POST /api/auth/google  →  { credential }
5. Backend verifica el JWT con Google
6. Crea o actualiza el usuario con google_id
7. Devuelve token de Sanctum

8. Integraciones Externas

Stripe — Pagos

Se usa Stripe Checkout Session para el depósito de reserva ($5 USD). El flujo es:

  1. Frontend crea la reserva en estado pending
  2. Backend crea una sesión de Stripe y devuelve checkout_url
  3. Usuario paga en la página de Stripe
  4. Stripe llama al webhook POST /api/payments/confirm-reservation
  5. Backend confirma la reserva y envía el correo

Si se cancela la reserva, el reembolso es automático vía PaymentIntent::cancel() o Refund::create().

Cloudinary — Imágenes

Las imágenes se suben directamente desde el frontend usando el widget de Cloudinary. Se guarda solo la URL en la base de datos. Variables requeridas: VITE_CLOUDINARY_CLOUD_NAME, VITE_CLOUDINARY_UPLOAD_PRESET.

Gmail SMTP — Correos

Se envían dos correos en cada reserva confirmada:

  • Al cliente: ReservationConfirmed.php — incluye datos de la reserva y código QR
  • Al propietario: OwnerNewReservation.php — datos del cliente y mesa

Configuración: puerto 465 (SSL), host smtp.gmail.com, usando App Password de Gmail.

QR — Validación de Llegada

Al crear la reserva se genera un código único (RYA-000001) guardado en qr_code. El propietario escanea el QR desde su panel usando la cámara, el sistema valida el código y puede marcar la reserva como completed.

12. Flujos Principales del Sistema

Flujo de Reserva Completo

Cliente selecciona restaurante
  → Elige fecha y escribe hora libremente
  → Sistema consulta GET /api/restaurants/{id}/availability
  → Backend verifica conflictos de ±90 minutos
  → Muestra mesas disponibles en tiempo real
  → Cliente selecciona mesa y activa depósito Stripe
  → POST /api/reservations  →  estado: pending
  → Backend crea sesión Stripe  →  devuelve checkout_url
  → Cliente paga en Stripe ($5 USD)
  → Stripe llama webhook → POST /api/payments/confirm-reservation
  → Backend cambia estado a confirmed
  → Envía correo al cliente y al propietario
  → Cliente ve reserva con código QR en /mis-reservas

En el restaurante:
  → Propietario escanea QR con la cámara
  → POST /api/owner/restaurants/{id}/reservations/scan
  → Sistema valida el código y marca como completed

Flujo de Cancelación y Reembolso

Cliente cancela desde /mis-reservas
  → PATCH /api/reservations/{id}/cancel
  → Si payment_intent_id existe y !deposit_refunded:
      - Si status = requires_capture → PaymentIntent::cancel()
      - Si status = succeeded → Refund::create()
  → Reserva queda en estado cancelled
  → deposit_refunded = true

14. Solución de Problemas Comunes

El servidor de Render tarda en responder

El plan gratuito de Render suspende el servidor tras 15 minutos sin tráfico. La primera petición puede tardar 30-60 segundos en "despertar" el contenedor. Es normal.

Los correos no llegan

Render bloquea conexiones SMTP salientes en algunos rangos de IP. Verificar en los logs de Render si hay errores de Connection timed out en el puerto 465. Alternativa: usar Resend con MAIL_MAILER=resend y RESEND_KEY.

Error 419 CSRF

No aplica para APIs con Sanctum y tokens Bearer. Si aparece, verificar que el frontend esté enviando el header Authorization: Bearer {token}.

CORS bloqueado

Verificar que CORS_ALLOWED_ORIGINS incluya la URL del frontend. En producción debe ser https://reservaya-3cbw.onrender.com.

Migraciones no corren en producción

Verificar que RUN_MIGRATIONS=true esté en las variables de Render. Las migraciones corren automáticamente en el script de inicio del contenedor.
